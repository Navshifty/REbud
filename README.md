# REbud

An AI-powered research intelligence and proposal analysis workbench.

Upload a research paper or proposal and get structured intelligence: an
overview, research gaps, a novelty assessment, critical analysis,
proposal relevance, related research, concrete suggestions, and a
context-aware AI discussion about the work.

REbud distinguishes between **evidence extracted from the uploaded
documents**, **AI-generated interpretation**, and **suggestions or
inferences**, so speculative output is never presented as fact.

## Status

Phase 4 (research intelligence) — uploaded PDFs, DOCX and text files are
parsed, chunked and indexed, and each analysis module is generated by
Claude against those passages. Every finding carries verbatim quotes
cited back to the source document, and the interface says whether a
result came from the model or is sample data.

Set `ANTHROPIC_API_KEY` in `server/.env` to analyse your own documents.
Without it the API serves clearly labelled sample results, and without
`VITE_API_URL` the frontend runs on an in-browser mock backend — so the
UI stays usable at every level of setup.

Still ahead (Phase 5): database, OAuth, tests, CI/CD and deployment.

## Getting started

**Frontend** (from the repo root):

```bash
npm install
npm run dev
```

Other scripts: `npm run build`, `npm run preview`, `npm run lint`
(lint covers `server/` too).

**API** (in a second terminal):

```bash
cd server
npm install
cp .env.example .env
npm run dev
```

Then point the frontend at it: copy `.env.example` to `.env` in the repo
root (it sets `VITE_API_URL=http://localhost:4000/api`) and restart
`npm run dev`. Create an account on the signup page; passwords need 8+
characters with upper, lower and special characters.

**Mock mode** — leave the root `.env` out and the frontend runs entirely
in the browser on sample data. Demo login: any valid email with the
password `correcthorse`.

### API overview

All routes are under `/api`; everything except `/auth/*` and `/health`
needs `Authorization: Bearer <token>`.

| Method | Route | Purpose |
| --- | --- | --- |
| POST | `/auth/signup`, `/auth/login` | Create an account / log in → `{ token, user }` |
| GET | `/auth/me` | Current user |
| GET, POST | `/projects` | List (with derived `summary`) / create |
| GET, PATCH, DELETE | `/projects/:id` | Read / update name, objective, archived / delete |
| GET, POST | `/projects/:id/documents` | List / upload (`files[]`, multipart, text extracted on upload) |
| POST | `/projects/:id/documents/:docId/reprocess` | Re-run text extraction |
| DELETE | `/projects/:id/documents/:docId` | Remove a document |
| GET, POST | `/projects/:id/analysis` | Module states / start modules (202, then poll) |
| POST | `/projects/:id/chat` | `{ topic?, messages }` → assistant reply |

Persistence is a JSON-file store under `server/data/` and uploads live in
`server/uploads/` (both git-ignored). A database replaces the store in
Phase 5 without touching routes or services.

### How an analysis runs

```
upload → extract text (pdf-parse / mammoth / utf-8)
       → chunk on paragraph boundaries, id each chunk (D1#3)
       → BM25 index; select the whole corpus, or the passages most
         relevant to the module when it is too large to send
       → Claude with a per-module JSON schema (structured outputs,
         adaptive thinking, prompt caching on the document block)
       → resolve cited chunk ids back to documents, dropping any the
         model invented; clamp scores; attach provenance
```

Each module's prompt and schema live in
`server/src/data/analysisSchemas.js`. Findings are required to carry
verbatim `evidence` quotes cited by chunk id, which is what keeps
document evidence separate from model interpretation in the UI.

Retrieval is lexical (BM25) and dependency-free, so no embedding
provider or second API key is needed. `lib/retrieval.js` is the seam if
you want to swap in embeddings later.
